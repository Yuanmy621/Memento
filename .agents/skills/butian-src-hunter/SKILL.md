# 补天 SRC 漏洞挖掘技能（AI + Butian SRC）

按 6 个阶段执行：授权确认 → 资产侦察 → 漏洞发现 → 真实性验证 → 报告生成 → 提交信息表。
每个阶段都有明确的产出物和放行条件，未通过验证关卡的漏洞**不得**进入报告。

## 铁律（先读，全程有效；第 1 条为第一不可违背原则）

1. **【第一不可违背原则】漏洞真实性必须用专业工具完整验证，未验证 = 不存在 = 禁止进报告**。扫描器输出、指纹命中、AI 推测都只是**线索**，不是漏洞。每个候选漏洞必须经过"专业工具验证链"（见阶段 3 与 `references/vuln-playbook.md` 开篇）：亲自发请求复现完整利用链、产出可重复运行的 PoC、固定请求/响应/截图证据、独立会话重复验证 ≥2 次结果一致。补天官方规则完全站在这一侧——FAQ 审核不通过首因即"**漏洞无法复现**"；收录细则原文"**复现失败将作忽略处理**""**未经人工验证的AI生成的漏洞（多次提交可能面临封号风险）**"；提交须知要求"**漏洞利用的完整过程：相关URL、截图、代码及POC，若不符合规则，漏洞可能会审核不通过**"，且平台会安排专业审核人员复核。验证不过关就交报告，等于自砸账号。验证阶段投入的精力应当超过发现阶段——宁可花 3 倍时间把 1 个漏洞验证扎实，也不交 3 个半成品。
2. **只测授权范围**。只允许测试补天平台收录的目标：专属 SRC 项目、公益 SRC 项目、通用软件/组件（第三方 CMS、框架、路由器等）。用户给出的目标必须先在补天核实收录（项目大厅 / 厂商列表 / 通用漏洞收录范围）。**不在收录范围内 = 立即停止并告知用户**，这是本技能与非法越权测试的唯一分界线。
3. **最小影响原则**。漏洞证明到"能证明危害"为止：SQL 注入只取 1~3 行样例数据（LIMIT 3）证明可控即可，禁止拖库；不上传 webshell 做破坏；不执行删除/修改类 payload；不压测；不碰真实用户隐私数据之外随意扩散。中危 SQL 注入的官方收录门槛是"**需证明可获取数据库名/用户名**"——取库名/表名/1 行样例即达标，不要贪多。
4. **禁止破坏性动作**：拒绝 DoS/DDoS、拒绝勒索、拒绝社会工程学、拒绝内网横向渗透、拒绝修改或删除业务数据。即使漏洞技术上支持，也只做只读验证。
5. **数据脱敏**。证据截图/请求包中出现的手机号、身份证、姓名、密码等一律打码（保留前 3 后 2 之类可辨识格式即可）。取证所需的最少数据量，展示给厂商看的也要脱敏。
6. **AI 报告合规**。基于第 1 条官方原文，本技能产出的报告必须在最后附"人工核验检查清单"，提醒用户提交前逐项亲自过一遍——提交者对真实性负全责。
7. **主动验证须逐项获得用户授权**。sqlmap、nuclei、定制 PoC（poc.py）等主动验证工具的**每一条命令**，执行前必须向用户展示"工具 + 目标 + 具体请求 + 预期影响与数据接触范围"，获得该单项的明确确认后方可运行；**不得默认自动执行，"一次性批准全部"视为无效**。确认只对当次"工具+目标+参数"有效：换目标、改参数、追加 payload 都要重新确认。被动收集（crt.sh、搜索引擎、Wayback）与正常页面访问不受此限；用户拒绝或未确认的项一律不执行。

## 阶段 0：授权与范围确认

向用户收集并确认（缺一项就先问，不要猜）：

- **目标**：补天项目名称/链接，或厂商名、主域名、通用软件名称（如"ECShop"、"某公益SRC的 example.com"）。
- **项目类型**：专属 SRC（有明确资产范围与规则）/ 公益 SRC / 通用漏洞。去 https://www.butian.net 项目大厅或厂商列表核实，把收录范围、测试限制、排除项记录下来。注意官方边界：**IP 漏洞暂不收取**；gov/edu 有单独权重要求；奇安信及关联公司员工不适用任何奖励计划。
- **明确排除**：不在范围的主域/子域、明确禁止的测试方式（如禁止扫描器大流量）、不涉及的资产。

产出：`out/01-authorization.md`（目标范围、收录依据、测试边界）。
**任何对范围外资产的探测都直接终止任务。**

**测试演练靶场选择**（当目的是"测试/演练本技能"而非真实提交时，目标可以是授权靶场，二选一）：
- **线上练习靶场（合法，平台明确授权测试）**：墨者学院（mozhe.cn）、合天（hetianlab.com）、攻防世界（adworld.xctf.org.cn）、BUUCTF（buuoj.cn）、i春秋、HackTheBox、TryHackMe——需用户本人注册登录并开通实验实例，实例地址即授权范围；只测自己开通的实例，不影响平台其他用户。
- **本机靶场（技能自带，演练默认用这个）**：`assets/lab/app.py`——零账号依赖、可重复、离线可用。
  - 启动：`python <技能目录>/assets/lab/app.py` → 监听 http://127.0.0.1:8899（仅本机 127.0.0.1，数据全虚构）
  - 内置埋点（用于检验本技能全流程；验收时不要向被测方提前透露埋点分布）：
    - [真] `/.env` 信息泄露（虚构的测试配置）
    - [真] `/api/user?id=<n>` SQLite 字符串拼接注入（布尔差异 + UNION 可取 sqlite_version/表名，满足官方"可取库名"门槛）
    - [假] `/admin` 静态登录页（"后台暴露"假阳性，无任何功能）
    - [假] `/search?q=` 输出被 html.escape 全编码（XSS 假阳性）
  - 验收标准：被测会话应产出 2 个真实漏洞的完整验证链（PoC/报文/证据）进报告，且 2 个假阳性被淘汰并写明淘汰理由——假阳性处理能力与真漏洞同等重要。
- **绝不**把"线上随便找的站点"当靶场——那不是演练，是越权违法。演练靶场的产出同样标注"演练数据，不可真实提交"。

## 阶段 1：资产侦察（被动优先）

先读 `references/butian-rules.md` 熟悉补天收录口径，再开始侦察。原则：被动信息收集优先，主动探测限速、限量。

1. **被动收集**（无请求打到目标或仅普通访问）：
   - 证书透明度：`https://crt.sh/?q=%25.<domain>` 拉子域
   - 搜索引擎语法：`site:target.com`、`site:target.com inurl:admin|login|api|upload`
   - GitHub/Gitee 代码泄漏搜索：`target.com` + password/config/jdbc 等
   - Wayback Machine 历史URL：`http://web.archive.org/cdx/search/cdx?url=*.target.com&output=text&fl=original&collapse=urlkey`
2. **主动探测**（限速进行，可用 `scripts/recon.py`——脚本自带授权门禁：运行必须加 `--authorized`，表示你已完成本阶段的补天收录核实，否则拒绝运行；TLS 证书校验强制开启；敏感路径仅 HEAD 探测，不做 GET 回退）：
   - 子域存活探测 + HTTP 指纹（标题、Server、框架特征、WAF）
   - 常见敏感路径 HEAD 探测：/.git/HEAD、/.env、/backup.zip、/admin、/swagger、/actuator、/phpinfo.php 等（只探测不利用）
3. **指纹归类**：CMS/框架/中间件版本 → 关联已知 CVE 与历史通用漏洞（通用漏洞是补天的重要收录类型）。

产出：`out/02-assets.md`（资产表：URL、标题、指纹、开放端口/路径、备注、候选风险点）。

工具优先级：本机装有 subfinder/httpx/nuclei 就用（nuclei 只跑 `severity: low,medium,high` 且排除 intrusive 与 DoS tags 的模板）；没有就用 `scripts/recon.py` + curl。扫描全程放慢（单线程或低并发 + 延迟），避免触发封禁与影响业务。

## 阶段 2：漏洞发现（找线索）

围绕补天官方关注的 10 类 Web 漏洞类型找线索（XSS、SQL注入、命令执行、代码执行、文件包含、任意文件操作、权限绕过、逻辑漏洞、信息泄露、存在后门；完整验证手法见 `references/vuln-playbook.md`）。**同时避开官方忽略清单**（url 跳转、self-xss、CORS 配置错误、邮件/短信轰炸、无敏感信息的 api 泄露、过期 key、拒绝服务测试等不作为主要目标）：

| 类别 | 典型线索 | 常见定级 |
|---|---|---|
| 越权（水平/垂直） | 接口带 id/uid 参数、隐藏管理接口 | 中危~高危 |
| SQL 注入 | 报错回显、布尔/时间盲注特征、搜索框/排序参数 | 高危 |
| 命令执行/反序列化 | 已知组件 CVE（log4j、fastjson、shiro、weblogic 等）、上传功能 | 高危 |
| 逻辑漏洞 | 0元下单、负数金额、验证码绕过、任意密码重置、短信轰炸 | 中危~高危 |
| 信息泄露 | .git/.env/备份文件、API 未鉴权返回敏感数据、源码包 | 低危~中危 |
| XSS | 存储点（个人资料、评论）优先于反射点 | 低危~中危 |
| 文件上传 | 上传点 + Content-Type/后缀校验逻辑 | 中危~高危 |
| SSRF | 带URL参数的功能（预览、导入、webhook） | 中危 |

方法：指纹命中已知 CVE 优先验证；手动参数测试（注入点、越权 id 改包）；接口未鉴权测试（不带 Cookie 直接请求 API）。

产出：`out/03-candidates.md`（候选清单：线索、初步判断、下一步验证计划）。此阶段允许大量候选是误报——下一步就是淘汰它们。

## 阶段 3：真实性验证（第一不可违背原则的执行关卡，不过不得写报告）

**验证授权关卡（强制，先于一切验证动作）**：

1. 进入本阶段前，先向用户提交"**验证计划清单**"：每项 = 候选漏洞 + 拟用工具 + 具体命令/请求 + 预期影响与数据接触范围，**经用户逐项明确确认后才可执行**（对齐铁律 7：sqlmap、nuclei、定制 PoC 每条命令单独授权，"一次性批准全部"无效）。
2. 用户拒绝或未确认的项一律不执行，写入 `out/05-rejected.md`（原因：未获用户授权）。
3. `scripts/recon.py` 内置授权门禁（运行须加 `--authorized`）、TLS 证书校验强制开启、敏感路径仅 HEAD 探测——不要绕过或关闭这些约束。

对每个候选漏洞，先读 `references/vuln-playbook.md` 开篇的"专业工具验证链"，再按对应漏洞类型条目执行完整验证。本阶段投入的精力必须 ≥ 发现阶段。

**专业工具验证链（按可用性分层，先探测本机装了什么）**：

| 层级 | 工具 | 用途与纪律 |
|---|---|---|
| 专业工具层 | sqlmap（`--batch --level=1 --risk=1 --threads=1 --dbs` 止步于库名，禁 `--dump` 全量）、nuclei（`-severity low,medium,high -exclude-tags dos,intrusive`，命中必手工复核）、pd httpx/subfinder、nmap `--top-ports` | 有就优先用：自动化确认快、输出规范可作证据附件；结果一律降级为"线索+初步确认"，仍需第 2、3 层闭环 |
| 定制 PoC 层 | Python requests/urllib 自写验证脚本（布尔/时间差对照、越权对照、签名绕过） | 每个确认的漏洞产出一个**可重复运行的 `poc.py`**（内置目标参数、断言、输出结论），这是"代码及 POC"证据的核心 |
| 取证层 | curl -v / httpx / 浏览器 devtools / browser-use 技能 | 原始报文与 GUI 截图取证；逻辑与越权类必须用浏览器以真实用户视角复现一次 |
| 兜底层 | 本机都没有时：curl + python 标准库手写全部请求，逐条固定报文 | 工具缺失不是跳过验证的理由 |

统一验证流程（每个候选必须全走）：

1. **完整复现利用链**：从正常状态 → 构造请求 → 危害结果，每一步亲自执行并记录请求与响应原文。
2. **危害闭环 A-B-C**：修改前状态(A) → 操作(B) → 修改后状态(C)。例如越权：A=用户甲的数据列表，B=把 id 改成乙的，C=返回了乙的数据。闭环缺失 = 无法证明漏洞 = 丢弃。SQL 注入必须证明到官方门槛（可获取数据库名/用户名/表结构）。
3. **排除误报**：蜜罐特征、扫描器通用回显、登录页/静态页假阳性、缓存污染、已修复（无痕会话 + 随机 cache-bust 参数重测）。扫描器报了但你复现不出 = 误报。
4. **重现性矩阵**：独立会话/无痕环境重复验证 ≥2 次、跨时间点 ≥1 次，结果必须稳定一致；时间盲注类必须带对照组（同请求无 payload 的基线响应时间）。
5. **证据固定**（存入 `out/evidence/<vuln-id>/`）：
   - `poc.py`：可重复运行的验证脚本（含断言与结论输出）
   - `request.txt` / `response.txt`：完整 HTTP 报文（curl -v 或工具原始输出）
   - `screenshot-*.png`：浏览器复现截图（browser-use 技能），敏感数据打码
   - `verify-notes.md`：复现步骤、时间戳、重现性矩阵结果、验证结论
6. **最小影响执行**：注入 `--dbs`/LIMIT 1~3 取证即停；越权只看 1~2 条他人记录；下载类泄露只取文件头部证明内容真实。

产出：`out/04-verified.md`（已验证漏洞清单，附每个漏洞的工具链与重现性矩阵）+ `out/05-rejected.md`（误报/无法复现清单及原因）。两者都写，误报淘汰记录同样是专业性的证明。

**质量门槛**：每个进入报告的漏洞，你要能回答——"厂商拿到报告后照 poc.py 与复现步骤做，能否 100% 复现？"答不上来就回炉重验；PoC 脚本跑不通 = 漏洞不成立。

## 阶段 4：生成补天规范漏洞报告

先读 `references/butian-rules.md` 的定级与标题规则，用 `assets/report-template.md` 生成 `out/report-<漏洞编号>.md`。硬性要求：

- **标题格式**：`【漏洞类型】厂商名/站点名-业务模块 存在 <漏洞名称>`，如 `【SQL注入】XX公司官网-搜索接口 存在 基于时间的SQL盲注`。一句标题说清 厂商+位置+类型。
- **等级判定（双轨制，对齐官方 DREAD 模型）**：先按官方 DREAD 公式打分——风险等级 = 潜在损失 + 重现性 + 可利用性 + 受影响的用户 + 可发现性（每维 0/1/2 分；1-4 低危、5-7 中危、8-10 高危），再对照官方三档描述（高危=RCE/getshell/大量敏感泄露/资金逻辑/管理密码重置；中危=一般注入需证明可取名/存储XSS/任意文件操作/越权/DB连接串泄露；低危=redis 未授权、heapdump、短信轰炸等）核对，两轨结论一致才定级。同样是注入，在核心业务库是高危，在废弃测试库里可能只是低危——定级理由必须写透（利用难度、影响面、数据敏感度）。
- **必含章节**：漏洞概述、影响范围（URL/资产/版本）、复现步骤（编号步骤 + 每步的请求/响应 + 截图引用）、危害证明（A-B-C 闭环）、危害分析（能造成什么实际损失）、修复建议（具体可执行，写清改哪里怎么改；官方要求认真填写，乱填/凑字会被扣分）、附录（证据文件清单，按官方"四件套"命名对齐：漏洞URL截图、归属证明、首页截图、漏洞证明）。
- **结果导向**：泄露类漏洞必须写出"泄露了什么"（如"泄露用户手机号与身份证号"），只写复现方式不写危害结果是最常见驳回原因。
- 全文中文，专业克制，不夸大不虚构。证据引用指向 `out/evidence/` 内的文件名。

## 阶段 5：生成提交信息填写表

用 `assets/submit-table-template.md` 生成 `out/submit-info-<漏洞编号>.md`（多漏洞时汇总一张总表）。表格字段对齐补天官方提交表单（`references/butian-rules.md` §7）：漏洞标题、厂商/项目、漏洞URL（GET 注入带完整参数拼接；POST 注入附完整数据包+注入参数）、漏洞类型、危害等级、DREAD 自评、**漏洞权重（公益/未注册厂商必选，以主域名爱站权重为准，权重0厂商务必显式选0，选错/漏选驳回）**、漏洞描述、复现步骤摘要、危害证明、修复建议、证据四件套（漏洞URL截图/归属证明/首页截图/漏洞证明，附件单个 ≤5M）、所属行业/行业分类/所属地区、厂商联系方式、留名/留QQ、参与活动/任务。目的：用户照表逐项复制粘贴到补天提交页面即可，不用再回头翻报告。奖励预期按 `references/butian-rules.md` §5-§6 的厂商权重分档估算（事件型按厂商规模 1-18KB 或现金；通用型重点应用 ¥200-10000、小众厂商 3kb-¥500）。

## 阶段 6：人工核验清单 + 交付

报告末尾必须附"人工核验清单"，并当面向用户重申（对齐补天 AI 报告规范——提交者对真实性负全责）：

- [ ] 我已亲自按报告步骤完整复现一遍（AI 代验不算，提交者本人算）
- [ ] 证据截图/报文是我自己生成的且未加工
- [ ] 目标在补天收录范围内、未超出测试授权
- [ ] 证据中敏感数据已脱敏
- [ ] 已在补天搜索确认非重复漏洞（重复判定以提交时间排序为准，先查厂商历史漏洞）
- [ ] 一洞一投，不multi投其他平台

最终交付：`out/` 目录下的 01~05 过程文件 + `report-*.md` + `submit-info-*.md`。向用户汇报：发现了什么、验证结论、定级理由、哪些候选被淘汰及原因。
