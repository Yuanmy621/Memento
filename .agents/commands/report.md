用户用 `/report` 触发了「漏洞报告成稿」流程。下面内联的《report — 漏洞报告成稿收口》
是这次任务的**唯一写作标准**，请完整遵守它（分层验证门、DOCX 版式、Step 式 PoC、
截图铁律、反 AI 腔、命名归档），不要凭印象另起一套格式。

执行顺序（与方法论一致）：

1. **先查重**：确认这不是已有报告的重复（同资产 + 同根因 + 同接口 + 同影响面）。
2. **过分层验证门**：硬门缺一就停下来说明缺什么、怎么补，**不要硬写**。
3. **生成 DOCX**：用同目录的 `template.docx` 作为版式基准；正文按 Heading 2 章节骨架走。
4. **截图**：每步都要真实目标站的截图（后台/headless 抓取），禁止伪造渲染图。
5. **命名归档**：语义化命名，落到约定目录。

配套资产（在 `.agents/skills/report/`，需要时用 `read` 工具打开）：

| 文件 | 用途 |
| --- | --- |
| `SKILL.md` | 方法论正文（本次已内联，需要逐字对照时可再读） |
| `template.docx` | DOCX 版式基准，生成报告时以它为模板 |
| `UPSTREAM-README.md` | 上游说明（含工作流图与效果预览） |
| `docs/demo-*.png` | 上游演示版式，用于对照章节骨架与 PoC 页长什么样 |

⚠️ 若目标是「还没确认的信号」而不是已确认漏洞：**不要写报告**，先回到挖掘/验证
（可用 `/skill src-hunter` 那套流程），等硬门过了再来 `/report`。
